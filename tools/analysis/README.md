# tools/analysis — ad-hoc population & GTFS-RT analysis scripts

> **Standalone analysis tooling.** Nothing in this folder is part of the easy-OTP QGIS plugin
> and none of it is imported by `easy_otp/`. These are one-off scripts written to answer
> specific research questions, kept here for reuse rather than thrown away. Edit the `CONFIG`
> block at the top of each script before running — every script leaves that block clearly
> marked and documents what each value means.

Two execution contexts are mixed in this folder:

- **QGIS Python Console scripts** (`population_by_isochrone_time*.py`) — need `qgis.core` /
  `qgis.PyQt`, so they only run inside QGIS: Plugins → Python Console → "Show Editor" → paste →
  Run (or as a one-off Processing "Script"). They operate on layers already loaded in the
  current QGIS project (looked up by name).
- **Plain Python scripts** (`gtfs_static_vs_realized_diff.py`) — pure stdlib, no QGIS needed.
  Run from any terminal with `py gtfs_static_vs_realized_diff.py` (per this repo's convention:
  `py`, not `python`).

Generated outputs (`.csv`, `.png`) are data, not code — same as everywhere else in this repo
(see the main `CLAUDE.md` `.gitignore` policy), so don't commit them; they're regenerated by
re-running the script.

## Isochrone / population scripts (QGIS console)

These three form a pipeline around one expensive step (the area-weighted population overlay)
and two cheap ones (plotting, numeric diffing) that read its result instead of recomputing it.

### `population_by_isochrone_time.py`

**What it does:** answers "how many people are within the isochrone at 06:00, 06:01, …?" for a
single isochrone layer. For every isochrone feature (one polygon per time step, optionally per
`cutoff_min`), area-weighted-interpolates population from every intersecting census tract
(same method as the plugin's `PopulationOverlay` algorithm: tract population ÷ tract area =
density; intersection-piece area × density, summed over all intersecting tracts, sped up with a
`QgsSpatialIndex` so it only tests candidate tracts). Writes the result into a new
`population_covered` field on the isochrone layer itself, then plots population vs. time (one
line per `cutoff_min`).

**Requires:** an isochrone layer already loaded in QGIS (output of `GenerateIsochronesOverTime`,
one polygon per time step, fields `time`/`cutoff_min`/`mode`/`date`) and a projected-CRS census
population polygon layer (e.g. EPSG:2180) with a numeric population field.

**How to run:** fill in `ISOCHRONE_LAYER_NAME`, `POPULATION_LAYER_NAME`, `POPULATION_FIELD`,
`OUTPUT_PNG_PATH` at the top, paste into the QGIS Python Console, run. Optionally narrow the
chart to a time-of-day window with `CHART_START_HOUR`/`CHART_END_HOUR`, adjust tick spacing with
`CHART_TICK_INTERVAL_MINUTES`, or override line colours with `CHART_COLOR_CYCLE` (all default to
today's full-range, default-colour, hourly-tick chart).

**Output:** `population_covered` field written onto the isochrone layer (in place) + a PNG chart
of population vs. time.

### `population_by_isochrone_time_compare.py`

**What it does:** the static-vs-GTFS-RT version of the script above. Runs the same
area-weighted overlay on **two** isochrone layers — one generated against a static GTFS graph,
one against a graph with a GTFS-RT `stop-time-updater` wired in — using one shared population
index (built once, reused for both) so the expensive part isn't duplicated. Plots both series
overlaid on one chart: static as circle markers, RT as square markers (no connecting line), one
colour per plotted line (see `CHART_COLOR_CYCLE` below), so the two are directly comparable.

Also fixes a display bug from the original script: PyQGIS returns `QDateTime`/`QTime` objects
for `time`-type fields, not plain Python `datetime`/`str` — the original code's fallback to
`str(value)` printed an unreadable `QDateTime(...)` repr on the x-axis instead of `HH:MM`. This
version converts to minutes-since-midnight explicitly (handling `QDateTime`, `QTime`, `datetime`,
and `str`) and formats ticks back to `HH:MM`.

**Requires:** two isochrone layers loaded in QGIS, generated with the same origin/mode/cutoffs/
time window — one static, one RT (see `tools/family_a_reconstruction`'s README, or a graph whose
`router-config.json` has a live GTFS-RT updater) — plus the same population layer as above.

**How to run:** fill in `ISOCHRONE_LAYER_STATIC_NAME`, `ISOCHRONE_LAYER_RT_NAME`,
`POPULATION_LAYER_NAME`, `POPULATION_FIELD`, `OUTPUT_PNG_PATH`; run in the QGIS Python Console.
Optionally narrow the chart to a time-of-day window with `CHART_START_HOUR`/`CHART_END_HOUR`,
adjust tick spacing with `CHART_TICK_INTERVAL_MINUTES`, or override line colours with
`CHART_COLOR_CYCLE` (all default to today's full-range, default-colour, 15-minute-tick chart).
`CHART_COLOR_CYCLE` assigns one colour per **plotted line**, in draw order (static then RT for
each cutoff, cutoffs in ascending order) — e.g. with a single cutoff, `["red", "blue"]` gives a
red static line and a blue RT line.

**Output:** `population_covered` field written onto **both** isochrone layers (in place) + one
overlaid comparison PNG chart.

### `population_by_isochrone_time_plot.py`

**What it does:** chart-only twin of `population_by_isochrone_time_compare.py`. Reads the
already-computed `population_covered` field from both layers and re-plots — no overlay
recomputation. Exists so you can try different chart titles / output paths without re-running
the slow geometry overlay each time.

**Requires:** the same two isochrone layers as above, but with `population_covered` **already**
populated (i.e. run `population_by_isochrone_time_compare.py` first).

**How to run:** fill in `ISOCHRONE_LAYER_STATIC_NAME`, `ISOCHRONE_LAYER_RT_NAME`, `CHART_TITLE`,
`OUTPUT_PNG_PATH`; run in the QGIS Python Console. Optionally narrow the chart to a time-of-day
window with `CHART_START_HOUR`/`CHART_END_HOUR`, adjust tick spacing with
`CHART_TICK_INTERVAL_MINUTES`, or override line colours with `CHART_COLOR_CYCLE` (one colour per
plotted line, in draw order — static then RT for each cutoff; see `_compare.py`'s entry above for
an example). Note: as of this change, the *default* line colours are matplotlib's default cycle
(matching `_compare.py`'s look), not the hardcoded red/blue this script used to draw — a
previously dead per-cutoff colouring bug was fixed alongside the new CONFIG options.

**Output:** one overlaid comparison PNG chart (same marker style as `_compare.py`'s chart, plus a
faint grey connector line between each cutoff's static/RT point pair at matching time steps).

### `population_covered_diff_static_vs_rt.py`

**What it does:** the numeric counterpart to the two chart scripts above — no chart, just
numbers. Reads `population_covered` from both layers (again, doesn't recompute it), pairs rows
by `(time rounded to the nearest minute, cutoff_min)`, and computes `diff = rt − static` per
matched time step. Time/cutoff steps present on only one side (e.g. a timestamp where the OTP
request failed and `GenerateIsochronesOverTime` skipped it) are reported as warnings, not
silently dropped.

**Requires:** same two isochrone layers, `population_covered` already populated.

**How to run:** fill in `ISOCHRONE_LAYER_STATIC_NAME`, `ISOCHRONE_LAYER_RT_NAME`,
`OUTPUT_DETAIL_CSV_PATH`, `OUTPUT_SUMMARY_CSV_PATH`; run in the QGIS Python Console.

**Output:**
- detail CSV — one row per matched time step: static, RT, `diff_rt_minus_static`, `diff_pct`.
- summary CSV — mean / mean(|diff|) / stdev / min / max diff, per `cutoff_min` and overall
  ("ALL" row). Same summary also printed to the console.

## GTFS comparison script (plain Python, no QGIS)

Two variants of the same underlying comparison exist side by side:

- **`gtfs_static_vs_realized_diff.py`** — the CLI version (below), used automatically by
  `easy-GTFS-RT`'s phone-build workflow. Fixed defaults, no in-place editing needed.
- **`gtfs_static_vs_realized_diff_config.py`** — the original CONFIG-block version, restored
  as its own file (2026-07-16) for ad-hoc runs where you want to hand-edit parameters (paths,
  chart hour window, bucket/tick sizing, colours) directly in the script rather than pass CLI
  flags each time — same convention as the isochrone/population scripts above. Not used by any
  workflow; edit the CONFIG block at the top, then run `py gtfs_static_vs_realized_diff_config.py`
  with no arguments. Logic is otherwise identical to the CLI version as of the commit just before
  the CLI conversion (`5c94dd1`) — the two will drift apart over time since edits to one aren't
  mirrored to the other.

### `gtfs_static_vs_realized_diff.py`

**What it does:** compares a static GTFS feed against its Family A "realized" reconstruction
(`tools/family_a_reconstruction`) to get a per-stop delay, even though neither file has a delay
field. Family A's `build` step rewrites `stop_times.txt` in place — byte-identical to the static
feed except corrected `arrival_time`/`departure_time` on segments the recording actually
observed; everywhere else keeps the original scheduled time (a "gap"). Because `trip_id`,
`stop_id` and `stop_sequence` are preserved unchanged between the two feeds, the script joins
`stop_times.txt` rows on that triple and computes `delay = realized_departure − static_departure`
per row (handles GTFS's after-midnight `25:00:00`-style times correctly).

A delay of exactly `0` is ambiguous — either "really ran on schedule" or "never observed, kept
as scheduled" — the script cannot tell the two apart from the GTFS files alone (only Family A's
own `build` console output, "Segments corrected" vs "Segments dropped", has that context). This
is why the chart step below drops zero-delay rows rather than plotting them.

**Requires:** a static GTFS `.zip` and a Family A realized `.zip` (`<prefix>_p50.zip` for the
median-observed variant, or `<prefix>_p85.zip` for the pessimistic 85th-percentile variant) built
from that same static feed. No QGIS. Chart generation additionally needs `matplotlib` — its own
`tools/analysis/requirements.txt`, deliberately separate from `tools/family_a_reconstruction/
requirements.txt` (that one is also installed on the Termux phone, TX-1, where matplotlib would
be dead weight with no prebuilt wheel for Android's Bionic libc anyway).

**This is a CLI**, not a fill-in-the-CONFIG script (as of the phone-release integration below —
every other script in this folder still uses the CONFIG-block convention). Run it with:

```bat
pip install -r requirements.txt
py gtfs_static_vs_realized_diff.py --static warsaw.zip --realized warsaw_realized_p50.zip --out-prefix out/warsaw_2026-07-15_p50
```

Flags:
- `--static` (required) — static GTFS `.zip` path.
- `--realized` (required) — Family A realized `.zip` path, built from `--static`.
- `--out-prefix` (required) — writes `<prefix>_summary.csv`, (if `--detail-csv`)
  `<prefix>_detail.csv`, and (unless `--no-chart`) `<prefix>_chart.png`. Include a directory in
  the prefix if you want the outputs somewhere other than the current folder (e.g.
  `--out-prefix out/warsaw_p50`).
- `--delay-time-field` — `departure_time` (default) or `arrival_time`.
- `--detail-csv` — also write the per-row detail CSV (off by default; the summary CSV is always
  written regardless of this flag).
- `--no-chart` — skip PNG chart generation; the summary CSV is always written regardless.
- `--chart-bucket-minutes` (default `15`), `--chart-start-hour`/`--chart-end-hour` (default:
  auto-cropped to the earliest/latest bucket with actual data — see chart notes below),
  `--chart-tick-interval-minutes` (default `30`), `--chart-tick-label-rotation` (default `45`),
  `--chart-line-color` (default `tab:red`), `--chart-bar-color` (default `grey`) — same knobs the
  old CONFIG block exposed, now CLI flags.
- `--chart-title-prefix` (default: none) — an optional extra line shown above the chart's title,
  e.g. `--chart-title-prefix "Lodz — 2026-07-15"`. The script has no notion of "city" or "date"
  itself (it only ever sees GTFS zips); the caller supplies this when it has that context — see
  "Used automatically in CI" below.

**Output** (all under `--out-prefix`):
- `<prefix>_summary.csv` — mean / mean(|delay|) / stdev / min / max delay, plus count and % of
  rows actually changed, per `route_id` and overall ("ALL" row). Same summary printed to the
  console. Always written.
- `<prefix>_detail.csv` — one row per matched `stop_times.txt` entry: `route_id`, `trip_id`,
  `stop_sequence`, `stop_id`, static/realized time, `delay_sec`, `delay_min`. Only written if
  `--detail-csv` is passed — this is per-row debugging output, not needed for day-to-day
  monitoring (the summary CSV covers that), and large enough per city per day that it isn't
  worth publishing by default.
- `<prefix>_chart.png` — mean delay (minutes) vs. scheduled time-of-day, bucketed every
  `--chart-bucket-minutes`. Rows with `delay_sec == 0` are excluded from this chart only (not
  from the CSVs) since they'd just wash the mean toward zero without meaning anything. A faint
  grey bar behind the line shows how many non-zero observations back each bucket, so you can
  judge how much to trust a given point. The x-axis is cropped tightly to the first/last bucket
  that actually has data (snapped to `--chart-bucket-minutes`) unless `--chart-start-hour`/
  `--chart-end-hour` override it explicitly — a partial-day recording (e.g. one that started
  hours into the nominal window) produces a chart matching that shorter span instead of a mostly
  empty one padded out to a fixed nominal window. **Not written** (silently, with a printed
  explanation) if every matched row has `delay_sec == 0`, or if `--no-chart` was passed — check
  stdout / the file's existence rather than assuming it's always produced.

**Used automatically in CI:** since the phone-recording pipeline (TX-8), `easy-GTFS-RT`'s
`family_a_build_and_notify_from_phone.yml` calls this CLI once per city per day (P50 variant)
right after publishing that day's realized GTFS release, and best-effort-uploads the resulting
chart + summary CSV onto the same release (never blocking the release itself — see that
workflow's "Generate static-vs-realized diff chart" step; it does not pass `--detail-csv`, so
that file is never produced or uploaded there). It does pass `--chart-title-prefix "<display
name> — <date>"`, using that city's `config/cities.json` `display_name` and the day being built,
so the chart is self-identifying once downloaded from the release rather than a bare "Mean delay
by scheduled time". Re-running it yourself against any day's released static + realized zips
reproduces exactly what that step does (add your own `--chart-title-prefix` if you want the same
labelling).
